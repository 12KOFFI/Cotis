GESTIONNAIRE
  - Crée et configure le groupe
  - Invite les membres par lien d'invitation (copie/partage SMS/WhatsApp)
  - Ajoute directement des membres (avec ou sans smartphone)
  - Enregistre les paiements manuels (cash/virement) avec justificatif optionnel
  - Gère les paramètres et tarifs du groupe (montant, adhésion, Wave)
  - Suit la caisse en temps réel (solde total + solde retirable Wave)
  - Décaisse depuis le solde retirable Wave
  - Exporte les rapports (PDF / CSV)

MEMBRE
  - Reçoit un lien d'invitation (SMS, WhatsApp, copier-coller)
  - Accède à son espace personnel (web)
  - Paie sa cotisation via Wave uniquement (initié par le backend)
  - Consulte son historique de paiements
  - Ne déclare JAMAIS de paiement — le backend est la seule source de vérité

SYSTÈME (automatique)
  - Calcule les statuts (À jour / Partiel / En retard / Impayé)
  - Traite les webhooks Wave (vérification HMAC via config())
  - Calcule les soldes dynamiquement depuis le ledger (jamais stockés)
  - Génère les périodes de cotisation automatiquement
  - Vérifie l'idempotence des paiements Wave (transaction_id unique)

2. CONFIGURATION DU GROUPE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Le gestionnaire configure son groupe en 2 étapes.

ÉTAPE 1 — Informations de base
  - Nom du groupe (obligatoire)
  - Type : Tontine / Coopérative / Association / Autre
  - Description courte (optionnel)
  - Logo (optionnel — upload image)

ÉTAPE 2 — Règles financières

  A. Droit d'adhésion unique
     - Activer : Oui / Non
     - Montant fixe (ex : 5 000 FCFA)
     - Pas d'échelonnement dans ce MVP — paiement intégral uniquement

  B. Cotisation récurrente
     - Fréquence : Hebdomadaire / Mensuelle / Trimestrielle / Annuelle
       → Si "Autre" : ouvrir un calendrier pour que le gestionnaire choisisse lui-même
     - Montant standard (ex : 2 000 FCFA)
     - Montant personnalisable par membre : Oui / Non (toggle, désactivé par défaut)
     - Date de début du 1er cycle
     - Pas de paiement échelonné dans ce MVP

  C. Caisse unique
     - Le groupe dispose d'UNE seule caisse
     - Tous les paiements entrants alimentent cette caisse
     - Le gestionnaire peut enregistrer des décaissements avec un motif

ÉTAPE 3 — Mobile Money Wave
  - Le gestionnaire saisit son numéro Wave (CI ou SN)
  - Ce numéro est affiché aux membres pour les paiements
  - Les webhooks Wave confirment automatiquement les transactions

3. GESTION DES MEMBRES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

3.1 — Ajout par invitation SMS / WhatsApp / Mail (canal principal)
  - Le gestionnaire saisit le numéro de téléphone du membre
  - Le système vérifie si un compte existe → lié ou créé à la volée
  - SMS / lien envoyé
  - Le membre clique → lien magique (auto-login sans OTP) → confirmation en 1 clic
  - Droit d'adhésion affiché si activé → paiement ou mise en attente
  [NOTE] Magic link : l'OTP classique est trop lourd pour l'adoption terrain.
          Le premier accès se fait par lien auto-login. L'OTP reste en fallback.

3.2 — Ajout direct par le gestionnaire (membres sans smartphone)
  - Le gestionnaire saisit : Nom, Prénom, Téléphone, Note
  - Membre ajouté en statut "Actif non vérifié"
  - Paiements enregistrés manuellement par le gestionnaire
  - Un LIEN D'ACCÈS SÉCURISÉ est automatiquement généré (access_token HMAC-SHA256)
  - Le gestionnaire peut copier ce lien et le partager (SMS, WhatsApp, etc.)
  - Le membre clique sur le lien → accès en lecture seule à son espace personnel
    (statut cotisation, historique des paiements, numéro Wave du gestionnaire)
  - Aucune inscription ni connexion requise pour les membres hors ligne
  [NOTE] Statut initial "Actif non vérifié" : évite les faux membres actifs.
          Le statut passe à "Actif" dès le premier paiement ou la confirmation.

3.3 — Statuts d'un membre

  STATUT       | DESCRIPTION                                       | INDICATEUR
  ─────────────┼───────────────────────────────────────────────────┼───────────
  À jour       | Montant de la période en cours entièrement versé  | ✅ Vert
  Partiel      | Partie versée, solde restant > 0 (période en cours)| ⚠️ Orange
  En retard    | Échéance dépassée, montant non réglé (période)    | ❌ Rouge

  [NOTE] Le statut est basé UNIQUEMENT sur la période en cours.
          Les retards des périodes précédentes apparaissent dans l'historique.

3.4 — Rôles (attribués par le gestionnaire)
  - Gestionnaire : accès complet (admin du groupe)
  - Trésorier : rôle attribuable à un membre par le gestionnaire.
    Droits du trésorier (identiques au gestionnaire, sauf suppression du groupe) :
      ✅ Accès au dashboard gestionnaire (KPIs, collecte, transactions)
      ✅ Enregistrement de paiements manuels (cash) avec justificatif
      ✅ Accès à la caisse (visualisation et décaissements)
      ✅ Gestion des membres (liste, détails, ajout)
      ❌ Ne peut PAS supprimer le groupe
      ❌ Ne peut PAS modifier les paramètres du groupe (tarifs, fréquence)
  - Membre standard : accès à son espace personnel uniquement

3.5 — Cotisation personnalisée par membre
  - Le gestionnaire peut activer le toggle "Montant personnalisable"
    dans les paramètres du groupe
  - Si activé : lors de l'ajout d'un membre, un champ "Montant personnalisé"
    apparaît (optionnel, par défaut = montant standard du groupe)
  - Calcul utilisé partout : montant_perso du membre ?? montant_standard du groupe
  - Impacte : dashboard, calcul des statuts, imputation des paiements

4. MODULE PAIEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

4.1 — Règles d'imputation des paiements

  Imputation par ancienneté
    → Tout paiement est imputé à la dette la plus ancienne en priorité.

  Gestion du surpaiement
    → Si montant payé > montant dû, l'excédent génère un crédit sur la prochaine période.
    Exemple : dû = 2 000 FCFA, payé = 3 000 FCFA → À jour + crédit 1 000 FCFA

  Paiement en retard multi-périodes
    → Le système identifie toutes les périodes impayées (ordre chronologique)
    → Le paiement solde les périodes dans l'ordre
    Exemple : 2 mois impayés (2 000 + 2 000), paiement de 3 000
              → mois 1 soldé (À jour), mois 2 partiel (1 000 restant)

4.2 — Paiement Wave (In-App) — Backend-Initiated
  IMPORTANT : Le paiement Wave est initié par le BACKEND, jamais par le frontend.
  Le membre ne voit qu'un bouton "Payer" — aucune clé API exposée côté client.

  Flux :
  1. Le membre clique "Payer" (un seul bouton, montant dû affiché)
  2. Le frontend appelle POST /groupes/{id}/paiements/wave-initiate
  3. Le backend crée la session Wave via l'API (clé stockée dans .env)
  4. Le membre est redirigé vers Wave pour confirmer (USSD ou push)
  5. Webhook reçu → vérification HMAC (config('services.wave.webhook_secret'))
  6. Vérification idempotente (transaction_id unique) → confirmation auto
  7. Écriture dans le ledger (entrée) → soldes recalculés dynamiquement

  [NOTE] Le membre ne peut PAS déclarer un paiement. Seuls le backend (webhook)
          et le gestionnaire (enregistrement manuel) peuvent créer des paiements.

  Statuts de paiement :
  STATUT      | DESCRIPTION
  ────────────┼──────────────────────────────────────────────
  En attente  | Paiement initié, en cours de traitement
  Réussi      | Webhook Wave confirmé OU enregistrement manuel
  Échoué      | Timeout ou solde insuffisant
  Annulé      | Cas exceptionnel, action manuelle

  [NOTE] Si Wave échoue, le gestionnaire peut enregistrer manuellement
          le paiement avec un justificatif (image/PDF, max 5 Mo).

4.3 — Paiement Manuel (Cash / Virement / Autre)
  Formulaire gestionnaire "Enregistrer un paiement" :
  - Membre concerné (sélection dans la liste)
  - Type : Cotisation / Droit d'adhésion / Autre
  - Montant (FCFA)
  - Mode : Cash / Wave / Virement / Autre
  - Date du paiement
  - Note interne (optionnel)
  - Justificatif (optionnel) : image JPEG/PNG/WebP ou PDF, max 5 Mo
    → Stocké de façon sécurisée, consultable depuis le détail du mouvement
  Résultat :
  - Écriture dans le ledger (entrée) → soldes recalculés dynamiquement
  - Enregistrement immédiat dans l'historique
  [NOTE] Traçabilité : tout paiement modifié est marqué "modifié"
          avec historique avant/après (JSON), identité gestionnaire et horodatage.
          Le justificatif est consultable dans le détail du mouvement de caisse.

4.4 — Droit d'Adhésion
  - Paiement Wave ou cash uniquement
  - Pas d'échelonnement dans ce MVP — paiement intégral
  - Suivi dans un onglet dédié
  - Relance SMS automatique si non réglé après 7 jours

  Statuts et accès :
  - Non payé (adhérent en attente) :
    ✅ Peut accéder à son espace personnel
    ✅ Peut consulter ses informations
    ❌ Ne peut PAS payer des cotisations
    ❌ Ne peut PAS être marquée "à jour"
    ❌ Pas de droits réservés aux membres
  - Réglé (membre) : accès complet

5. CAISSE UNIQUE — ARCHITECTURE FINTECH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  - UNE seule caisse par groupe (V2 → multi-caisses)
  - Tous les paiements entrants (Wave + cash) alimentent la caisse via ledger

  PRINCIPE FINTECH FONDAMENTAL :
  Les soldes ne sont JAMAIS stockés manuellement. Ils sont calculés
  dynamiquement depuis le journal de mouvements (ledger), comme dans
  les applications fintech modernes (Wave, Orange Money, etc.).

  → Chaque entrée/sortie génère une ligne immuable dans le ledger
  → Les soldes sont des agrégats SQL temps réel
  → Zéro risque de désynchronisation entre le solde affiché et la réalité
  → Audit trail naturel : toute valeur est traçable

  DEUX SOLDES DISTINCTS :

  SOLDE           | CALCUL                                | SIGNIFICATION
  ────────────────┼───────────────────────────────────────┼──────────────────────────────
  Solde total     | SUM(entrées) - SUM(sorties)           | Tout l'argent du groupe
                  |                                       | (cash + wave + virement)
  ────────────────┼───────────────────────────────────────┼──────────────────────────────
  Solde retirable | SUM(entrées WHERE mode = 'wave')      | Montants reçus via mobile
  (disponible)    |                                       | money uniquement — retirable
                  |                                       | sur le compte Wave du
                  |                                       | gestionnaire

  [NOTE] Le solde retirable représente l'argent réellement disponible dans
          le compte Wave du groupe, que le gestionnaire peut retirer.
          Les paiements cash sont déjà physiquement en main.

  Vue Caisse (Frontend) :
  ┌────────────────────────────────────────┐
  │  SOLDE TOTAL DE LA CAISSE              │
  │  1 500 000 FCFA                        │
  │  Entrées: 2 000 000  │  Sorties: 500K  │
  └────────────────────────────────────────┘
  ┌────────────────────────────────────────┐
  │  SOLDE RETIRABLE · WAVE                │
  │  800 000 FCFA            [Décaisser]   │
  │  Montant reçu via mobile money         │
  └────────────────────────────────────────┘

  Décaissement (gestionnaire / trésorier) :
  - Montant (vérifié contre le solde retirable Wave)
  - Motif (obligatoire)
  - Bénéficiaire (optionnel)
  - Date
  - Valider → écriture ledger (sortie) → soldes recalculés dynamiquement

10. LOGIQUE MÉTIER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Statut Cotisation par Période
  STATUT       | CONDITION
  ─────────────┼──────────────────────────────────────────────────────────
  À jour ✅    | versé = montant dû de la période en cours
  Partiel ⚠️  | 0 < versé < montant dû de la période en cours
  En retard ❌ | date dépassée ET versé < montant dû de la période en cours

  Formules de Calcul (dynamiques — jamais stockées)
    - Taux de collecte (%) = (total reçu / total attendu) × 100
    - Solde total       = SUM(entrées ledger) − SUM(sorties ledger)
    - Solde retirable   = SUM(entrées ledger WHERE paiement.mode = 'wave')
    - Reste à payer     = montant dû − montant versé (période en cours)
    - Crédit reporté    = surpaiement période N → déduit du montant dû période N+1

  [NOTE FINTECH] Les soldes sont des accesseurs Eloquent calculés via
    une requête SQL agrégée sur le ledger. Aucun champ "solde" n'est
    incrémenté/décrémenté manuellement. Cela élimine les race conditions
    et garantit la cohérence permanente entre le ledger et l'affichage.

11. ARCHITECTURE TECHNIQUE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Backend
    - API REST — PHP Laravel
    - Authentification : magic link (auto-login) + OTP SMS en fallback
    - JWT avec expiration courte
    - File de jobs asynchrones : Redis + Horizon
    - Jobs planifiés : rappels SMS, calculs de statuts

  Frontend
    - Next.js (dernière version, sans TypeScript)

  Base de Données — Tables MVP
  TABLE             | CONTENU
  ──────────────────┼──────────────────────────────────────────────────────────
  users             | Profil, téléphone, magic link token, OTP fallback
  groupes           | Config, fréquence, montant, modules actifs
  membres           | user ↔ groupe, statut (actif/non_verifie), montant perso
  invitations       | Token, canal, expiration, statut
  periodes          | Cycles, dates début/fin
  paiements         | Montant, statut, mode, date, type, modifié, historique_json
  paiements_log     | Avant/après modification, auteur, horodatage
  adhesion_frais    | Montant dû, payé, statut par membre
  caisse            | Nom, groupe_id (solde calculé dynamiquement via ledger)
  caisse_ledger     | Type (entrée/sortie), montant, motif, date, ref_paiement_id
  credits_membres   | Membre, montant crédit, période source, appliqué_periode

  Webhook Wave
    - Endpoint dédié avec validation signature HMAC
    - Secret webhook via config('services.wave.webhook_secret') — jamais env() direct
    - Vérification idempotente : transaction_id unique avant tout traitement
    - Doublon : ignoré silencieusement, log enregistré
    - Retry automatique : 3 tentatives (30s, 5min, 30min)
    - Écriture ledger après confirmation → soldes recalculés dynamiquement
    - Log immuable de chaque transaction

  Variables d'environnement Wave (.env) :
    - WAVE_API_KEY         : Clé API Wave (jamais exposée côté client)
    - WAVE_WEBHOOK_SECRET  : Secret HMAC pour valider les webhooks
    - WAVE_SUCCESS_URL     : URL de redirection après paiement réussi
    - WAVE_ERROR_URL       : URL de redirection après paiement échoué

14. UX / UI — PRINCIPES DE CONCEPTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Contraintes UX (prioritaires)
    - Interface très simplifiée
    - Icônes explicites + textes courts + langage simple
    - Navigation guidée (boutons clairs : "Payer", "Voir mes paiements", etc.)

    - Feedback visuel clair après chaque action (succès, erreur)

    - Messages rassurants après paiement

15. POINTS CLÉS À RESPECTER SCRUPULEUSEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. Seul le GESTIONNAIRE crée son compte en premier, crée le groupe,
     puis envoie un lien d'invitation (mail / SMS / WhatsApp) aux adhérents.

  2. Un adhérent devient MEMBRE uniquement après paiement de l'adhésion
     (si définie par le gestionnaire).

  3. Période "Autre" → ouvrir un calendrier pour sélection manuelle.

  4. Chaque membre ET gestionnaire a une CARTE VIRTUELLE téléchargeable
     avec QR code dans son profil. Le QR code affiche l'historique de cotisations.

  5. Le gestionnaire peut attribuer le rôle "Trésorier" à un membre.

  6. Le gestionnaire peut exporter les statistiques en PDF ou CSV.

  7. Les soldes (total et retirable) sont TOUJOURS calculés dynamiquement
     depuis le ledger — jamais stockés ni incrémentés manuellement.

  8. Le paiement Wave membre est initié par le BACKEND uniquement.
     Aucune clé API n'est exposée côté frontend.

  9. Le membre ne peut PAS déclarer de paiement. Seuls le backend (webhook Wave)
     et le gestionnaire (enregistrement manuel) peuvent créer des paiements.

  10. Les paiements manuels supportent un justificatif optionnel
      (image JPEG/PNG/WebP ou PDF, max 5 Mo).
